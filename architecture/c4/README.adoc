= TaviX C4 architecture
:toc:
:sectnums:

== Scope and authoritative model

`workspace.dsl` is the source of truth for TaviX C4 architecture (initial model for version 0.1.8, based on the TaviX 0.1.7 implementation). The model starts at Level 3 and includes minimum Level 1/2 views, two important dynamic flows and a source-supported local-development deployment view.

TaviX is an independent software system: immutable extension-package staging, a canonical static catalog, validation and QA, and a loopback developer preview/installer. It is *not* the Tavi messenger, the Atrium game lobby, Companion's engine, a game server, an identity provider, or an authenticated Tavi host runtime. Hosted/compiled extension payloads are distributed artifacts, not implementation of TaviX's own functional components.

The model does not invent remote services beyond observed source contracts. Relationships to GitHub Pages and Tavi are at the integration boundary; their internals are deliberately omitted. The hosted deployment topology is not modeled, because this source archive contains no source-controlled `.github/workflows/` or cloud configuration. A GitHub Pages workflow was observed separately for an older remote commit, but it is not a TaviX-owned executable in this source ZIP.

The small browser UI currently lives in one HTML file, but its three functional responsibilities are separate logical components, *not* claims about separate deployables or JavaScript modules. The Python package codec is source-reused by the loopback installer; this is a library call, not a network hop. The adapter is limited to the Companion producer's current build convention and is not a generic Atrium build service.

== System boundaries and external contracts

* *Extension producer* (external): supplies compiled extension bundle for optional post-build staging. A producer's own build, assets and business logic are not TaviX components.
* *Tavi* (external): discovers published catalog/assets over HTTPS and owns production embedded loading, SDK permissions, authentication and runtime sandboxing; none is modeled inside TaviX.
* *ZipRunner* (external): applies source ZIPs, invokes configured Python verification commands, tracks review/workboard state and gates authorized Git actions. TaviX source tools do not push themselves.
* *GitHub repository and Pages* (external): provides Git versioning and approved static distribution of catalog/assets. Source code references canonical base `https://thebigtreeinc.github.io/tavix/`. Do not treat local index updates as publication.
* *Extension maintainer*: invokes CLI and browser preview, reviews exact Git diffs and approves or rejects publication manually.

== Critical workflows

=== Stage a compiled release

A producer executes optional adapter -> Python `repository.py stage` -> archive validation/packing -> immutable versioned `extensions/<id>/<version>/` -> atomic canonical `tavi.repository.json` update. ZipRunner and operator Git review are separate. The model shows an *approval gate*, not an automatic Git push.

=== Install and preview a local package

Browser sends the `.tavix` bytes to loopback HTTP POST -> installer validates archive and extraction limits -> files are stored under `.tavix-local` -> browser lists installed metadata and loads the panel using local HTTP paths. File-picker behavior is a browser file input. The chosen "test account" is a *visual marker only*. The preview iframe is sandboxed but the local origin is not a hardened trust boundary.

== Verified deployment scope

The local preview server binds `127.0.0.1` and defaults to port `8765` (`tools/local-client/server.py`); the HTML UI runs in a local browser, while the Python runtime reads static checkout files and local installed packages. The operator's Windows host is a known environment from ZipRunner reports, but the same source is not Windows-exclusive. Remote GitHub Actions / Pages deployment internals, Tavi Windows/Android integration and LoopRD servers are outside the verifiable source topology.

== Explicit limitations and exclusions

* Archive hashes validate file integrity but do *not* prove publisher authenticity or trust. Permissions are shown as metadata; this is not production permission enforcement.
* The current archive codec validates included file hashes and main panel/icon existence, but does not yet comprehensively validate every transitive HTML/CSS/JS asset reference. There is a known improvement ticket to add missing-reference detection.
* Local preview does not expose the real Tavi host SDK, real identities, or multiplayer. No claim is made about Checkers logic, authoritative game servers or two-client acceptance.
* No independent SQL database, queue, background worker, WebView2 desktop executable or hosted API is present in this TaviX source. Source-bound release files and local development storage are modeled as file stores.
* A remote GitHub Pages deployment was observed for an earlier commit; the current source ZIP does not itself include `.github/workflows/pages.yml`. No new deployment or CI claim should be inferred from this architecture model.
* The precise Windows startup and browser memory behavior of Companion 0.6.37 is not captured by this source; it belongs to the Tavi/Companion runtime investigation, not the TaviX C4 baseline.

== Validation and maintenance

To validate with a separately installed Structurizr CLI (not bundled in the ZIP):

[source,powershell]
----
structurizr validate -workspace architecture/c4/workspace.dsl
----

With the legacy CLI distribution, use `structurizr.bat validate -workspace architecture/c4/workspace.dsl` on Windows or `./structurizr.sh validate -workspace architecture/c4/workspace.dsl` on Linux. The documented CLI should be independently installed and trusted; ZipRunner does not download it and no new release gate is silently introduced.

Local source sanity checks:

[source,powershell]
----
python -m unittest discover -s tests -v
python tools/repository.py check --repository . --strict
----

Whenever a TaviX-owned component, communication path, persistence dependency or external contract changes, update both this AsciiDoc and `workspace.dsl` within the same source pass. Preserve view keys and stable element identifiers. Reference an ODPS capability description if one is added in future rather than copying its body into C4. The test fixture asserts that these architecture documents remain at their root-relative paths; this does not substitute for Structurizr validation.

== Developer contract references (0.1.9 documentation maintenance)

The stable integration/documentation index is `../../docs/INDEX.adoc`; wire and package rules are described in `../../docs/TAVIX_CONTRACT.adoc` and `../../docs/TAVIX_PACKAGE_FORMAT.adoc` with a machine-readable discovery snapshot at `../../contracts/tavix-1.0.json`. This documentation-only addition introduces no new TaviX runtime components, boundaries or deployment paths, so the 0.1.8 Structurizr model remains unchanged.

== Classification extension (0.1.10)

The existing `package` component now also consumes the validated `tools/tavix_classification.py` policy and rejects invalid optional `manifest.classification` values. The existing `installer` and `discovery` components expose normalized classification to the local development UI, which displays game/app labels. They do not introduce a production host, a trusted registry, network identities or an Atrium game launcher. Tavi's required registry, restricted read-only installed-game inventory and host-mediated launch are specified *as external future integration* in `docs/TAVIX_CLASSIFICATION.adoc` and `contracts/tavix-installed-games-v1.json`; they are not modeled as implemented TaviX components or relationships. The published `.tavix` release tree remains unchanged and older manifests default to app/[].

== Asset request and host-grant boundary (0.1.11)

The CLI container now contains `assetContract`, implemented by `tools/tavix_asset_dependencies.py` and `tools/tavix_asset_grants.py`. `package`, `stage` and the local preview installer/discovery validate optional manifest asset requests and permission tokens. The preview lists requested pack IDs but never grants access. The grant checker is a pure *shape/subset* reference for a future Tavi host; TaviX never issues or persists runtime grants. No new runtime communication to Tavi Assets, LoopRD or the Wallet is implemented by this source change. External source evidence is Tavi 0.3.141 `client/src/assets/host-bridge.js` and `client/src/main.js`, and Tavi Assets 0.1.7 `contracts/tavi-assets-consumer-v1.json`. Details: `../../docs/TAVIX_ASSET_DEPENDENCIES.adoc`. The Tavi host's currently dormant asset engine and the separate Tavi Assets storefront are intentionally not modeled as TaviX-owned components.


== Proposed registry administration contract (0.1.12)

The TaviX-owned `tools/tavix_registry_admin.py` only recognizes a *manifest request* for `assets.registry.admin/v1`. `contracts/tavix-registry-admin-v1.json` and its request/response JSON Schemas define a proposed host-mediated interface. Tavi/Social (external) owns exact-revision host approval, native confirmation and trusted forwarding; LoopRD (external) is authoritative for `ecosystemAdmin`, registry operations, pricing, publication and revocation; Tavi Assets (external) validates canonical data-only `.tavia` packs. None of these external implementations live in TaviX. The local preview remains untrusted, and the proposed admin feature is not live in Tavi 0.3.141.


== Host-mediated native file import proposal (0.1.13)

The TaviX-owned `localFileContract` component validates `files.local.import` and the paired `manifest.fileImports` filter declaration; the package codec, repository stage and local-only installer/discovery use the same request validator. The new `sdk/tavix-sdk.mjs` and `examples/local-file-import` provide a *reference client*, not a production host. Tavi/Social (external) must implement Windows and Android native pickers, bounded read handles and detached-window session routing. No new TaviX backend, filesystem service, runtime grant or LoopRD communication is introduced. The source-local SDK mock tests validate wire shapes only. See `../../docs/TAVIX_LOCAL_FILE_IMPORT.adoc` and `../../contracts/tavix-local-file-import-v1.json`.
